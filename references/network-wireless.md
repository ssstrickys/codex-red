# Network and wireless protocol mechanisms

Protocol meaning depends on roles, version, topology, identity/authentication, replay protection, state and key lifecycle. Capture interface/channel, filtering, packet loss, time synchronization and tooling can change the available observations. A packet seen on an interface does not establish its acceptance by the peer.

Framing, negotiation, naming/resolution, authentication binding, routing and segmentation enforce different boundaries. Parser divergence and network loss can produce similar externally visible failures. Segmentation, retransmission, replay windows and key-epoch transitions have protocol-specific semantics. Active protocol operations remain subject to the task's target and rate scope.

## Wire representation and peer state

A TCP write, segment and application message need not share boundaries. Connection identity, direction, sequence space, retransmissions, reordering, gaps and overlapping bytes determine transport-stream reconstruction. IP fragmentation and transport reassembly occur at different layers, with receiver-specific policy where specifications leave choices. Application buffering, half-close/EOF and timeouts can change when a parser commits a message. Missing or ambiguous stream intervals leave their bytes unresolved. NIC offload can make a local capture show unusual checksums or segmentation that was not present on the wire.

Advertised capability, offered options, negotiated mode, authenticated identity, established keys and accepted application actions are distinct states. A successful transport handshake is not application authorization. Resumption, renegotiation, rekeying, sequence rollover and reconnects can change the context in which a frame is valid. Counters/nonces and replay windows belong to a specific peer, direction and key epoch; accepting an intentional protocol retransmission is not necessarily replaying an application action. Conversely, a cryptographically valid message can still violate an object or state authorization rule.

Low-volume control exchanges can define session or key state for a larger data stream. The association between control and data traffic, including active versus stale key material, determines payload interpretation.

A DNS authoritative record, recursive cache answer, host stub result and application-resolved destination are different observations. Query/response matching includes the relevant tuple, name, type and transaction context; cache admission/bailiwick policy and DNSSEC validation are separate controls. A forged-looking response is not evidence that a resolver cached it. Rebinding depends on client/application resolution, caching, origin/host checks, address restrictions and network reachability; a changed DNS answer alone does not establish access to an internal service. mDNS, LLMNR and NBT-NS have different scopes and consumers; one accepted name answer does not imply successful credential use.

Segmentation depends on the actual ingress port, VLAN membership/tag handling, routing and destination policy. A DTP frame requires a port that will negotiate; a static access port does not become a trunk because a tool transmits one. Double-tag behavior depends on the native-VLAN/tag-processing path and can be one-way; receipt of a tagged packet is not proof of a bidirectional session. MAC authentication bypass treats an address as a selector/credential under a particular policy, whereas certificate-based 802.1X binds a different identity. A port's authenticated state need not authorize every downstream device or resource.

IPv4 and IPv6 can provide separate effective paths. Router advertisements, SLAAC, DHCPv6, DNS selection and default-route decisions have different roles. DHCPv6 does not itself supply the IPv6 default router. OS policy, guard features, topology and the actual resolver/service determine whether an observed advertisement changes traffic; dual-stack support does not imply a preference for every supplied IPv6 resolver. TLS certificate validation, protocol signing and channel binding can constrain application impersonation even when routing or name resolution has changed. A network-position advantage alone does not establish compromise of an application boundary.

802.11/EAP/WPA behavior depends on AP/client role, negotiated security, certificate validation, transition modes, protected management behavior and replay handling. LE/GATT and BR/EDR profiles have different Bluetooth pairing/bonding and authorization conditions. Mesh/sub-GHz protocols depend on the actual stack/version, commissioning mechanism, nonce/counter behavior and physical capture conditions.

## Wi-Fi authentication and management

Wi-Fi key-exchange interpretation depends on BSSID, client/session, band, channel/width and negotiated AKM/cipher. An RSN advertisement describes offered policy; the particular association establishes what was negotiated. WPA2-Personal password-derived key material and WPA3-SAE are different authentication mechanisms. SAE establishes a PMK and is followed by the four-way handshake for link keys; WPA3 does not eliminate that handshake. A passive SAE exchange is not the ordinary WPA2 offline-password-verification problem. PMKID verification and EAPOL-MIC verification have different derivation inputs: the correct AP/client identities and, for the relevant EAPOL exchange, nonces, key context and covered message bytes. A tool's handshake label alone is not proof that all needed material is present.

Transition mode does not guarantee a client will fall back: the saved profile, client protections and actually selected AKM matter. Similarly, the presence of H2E signaling is not a blanket proof that every SAE implementation or surrounding state machine is secure. Historical vulnerability applicability depends on the implementation, negotiated method and vendor fix, not generic OS age. Key reinstallation, fragment-cache handling and aggregation faults concern distinct state transitions; they are not PSK recovery, and PMF alone does not settle all such flaws.

Enterprise access depends on the outer EAP method, any inner method, server-certificate trust/name policy, client authentication and resulting authorization. PEAP/TTLS inner credentials are protected by a TLS tunnel only to the peer the client actually validates. EAP-TLS uses client certificates and has different credential/authorization conditions from a password challenge. A trusted CA by itself need not constrain the expected authentication-server name. An outer identity can differ from the authenticated inner identity. Capturing an exchange or operating a lookalike SSID does not demonstrate a usable credential or defeat server validation.

PMF protects applicable robust management frames for a negotiated protected association; it does not authenticate every beacon or every action frame, nor prevent radio interference. Capable, required and actually negotiated protection are distinct facts. Management-frame behavior is specific to frame subtype, association state and peer handling; deauthentication rejection alone does not determine other action-frame behavior. 6 GHz operation depends on applicable Wi-Fi certification/security rules, enhanced-open OWE where supported, client profile and regional availability; WPA3-Personal is not the only relevant configuration. MLO can place one logical connection on multiple links, so a single-channel capture can miss relevant traffic.

WPS advertisement, PIN enrollment, push-button enrollment, random-secret generation and lockout behavior are separate observations. A chipset name is not proof of weak randomness or a current vulnerable firmware revision. Passive observation does not establish that online enrollment attempts were accepted. Roaming to a lookalike AP requires the client's profile and authentication to accept it; shared SSID, stronger signal or a matching BSSID does not force that outcome. Association with an untrusted gateway also does not defeat correctly validated HTTPS or application authentication.

## Bluetooth and personal-area networks

BLE advertising/discovery, connection, pairing, encryption, bonding and application authorization are different states. GATT services/characteristic properties advertise operations; per-attribute permissions and server-side checks determine whether a particular peer may perform them. Subscription/notification access differs from command write authority. A vendor UUID is not itself a privileged interface. App-to-characteristic payloads and device-side state determine the meaning of the requested operation.

Application-fragment reconstruction depends on connection/channel, record identity, sequence rules, gaps, conflicting copies and encoding/error semantics. A decoded export may already be decrypted, and authenticated fragments do not establish a complete or ordered record.

Just Works can establish an encrypted link without authenticated protection against an active pairing intermediary; it is not equivalent to no encryption. LE Legacy Pairing and LE Secure Connections have different derivations. Passive recovery of weak legacy pairing material does not imply passive key recovery from ECDH-based Secure Connections, even when its association method is unauthenticated. Numeric comparison, passkey entry and out-of-band association have their own user/credential assumptions. An existing bond, an application token, distance/proximity checks and relay resistance are separate boundaries; cryptographic pairing does not by itself prove physical proximity.

BR/EDR is not synonymous with old Bluetooth version numbers: modern dual-mode devices can support both transports. SDP service discovery and profile connection do not establish unauthenticated file, audio, HID or serial access. Historical controller/host vulnerabilities and key-length negotiation defects depend on the actual firmware, profile, security mode and negotiated state. A discoverable address or vendor OUI does not establish those conditions. Randomized addresses, shared adapters and changing resolvable/private addresses limit device/person attribution.

Zigbee network keys, trust-center/link keys, transport-key derivation, APS/application protection and command authorization provide separate properties. Capturing the relevant commissioning frames and obtaining the right key material are different requirements from reading ordinary traffic. A known commissioning/master value is not automatically the current network key, and possession of a network key does not establish that every protected application command will be accepted.

Thread is an IPv6/6LoWPAN mesh with a specific commissioning and network-key model; PSKc concerns commissioner authentication and is not simply the network master key. Matter is an application protocol over IP, commonly using Thread, Wi-Fi or Ethernet; it is not a common security layer for ordinary Zigbee devices. Matter's password-authenticated commissioning session, device attestation, fabric credentials/operational sessions and access-control entries have distinct roles. A setup code or access to the underlying Thread network does not by itself grant control of an existing Matter fabric. Z-Wave behavior depends on S0 versus the negotiated S2 security class and inclusion context. A historical S0 bootstrap-key weakness concerns the relevant inclusion exchange, not a universal known operational key. An S2 device-specific identifier/code supports the intended authentication procedure; it is not the device's private key or automatic command authority.

## LPWAN and physical capture conditions

LoRaWAN PHY visibility, join authentication, session derivation, network integrity and application-payload encryption are separate properties. The OTAA Join-Request is integrity-protected rather than encrypted. Join-Accept protection and session derivation depend on protocol version and key roles; session keys are derived from the required join context and root material rather than read as plaintext keys from a Join-Accept. LoRaWAN 1.0 uses AppKey for root-key roles that 1.1 separates between NwkKey and AppKey. For ABP or OTAA, frame counters, resets, rollover and replay acceptance depend on the actual device/server session policy; a changed capture timestamp is not a fresh authenticated uplink. A device address is not a secret. Knowing an application encryption key does not automatically satisfy network integrity or command authorization.

Proprietary sub-GHz and other RF payload interpretation depends on carrier, bandwidth, modulation, symbol timing, framing, coding/whitening and integrity. Fixed codes, rolling codes and challenge-response have different replay conditions. A captured waveform or successful local retransmission does not establish that the intended receiver accepted a command. Receiver sensitivity, interference, antenna placement, capture bandwidth and oscillator drift can cause missing frames. Passive reception, channel hopping, monitor-mode support, frame injection and peer delivery are different adapter/driver/firmware capabilities. Radio operations remain constrained by the applicable configuration and authorized scope.

A discovered SSID, MAC, open service or captured exchange does not establish a completed compromise or permission to act on nearby third-party devices. Protocol and vendor-specific behavior depends on the actual version, configuration and applicable primary specification or advisory.

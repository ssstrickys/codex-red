# Web, API and authentication security

An application boundary depends on the endpoint, method, transport, schema, authenticated identity, role, tenant, object ownership and current state. Different request representations can reach different parsers, handlers or authorization policies.

| Surface | Mechanism and limits |
| --- | --- |
| Authorization/IDOR | Object access depends on the authenticated principal and applicable resource policy, including nested relationships and tenant scope |
| SQL/command/template injection | Injection requires caller-controlled data to acquire meaning in an interpreter's grammar; errors alone do not establish execution |
| XSS | HTML/attribute/JS/URL context, browser interpretation, sanitization and CSP determine whether data becomes executable script |
| SSRF/XXE | Server-side fetches and parser resource resolution differ from browser requests; method, headers, destination and returned data affect impact |
| Upload/deserialization | Detection, decoding, storage, type construction and later consumption can interpret the same input differently |
| HTTP desynchronization | Frontend/backend framing disagreements can affect request boundaries; a timeout alone does not establish cross-request interference |
| Roles/field binding | Function-level authorization and writable-field policy are separate; a hidden UI field does not constrain server-side writes |
| Resource limits | Quotas depend on accounting scope, units and actual consumed work; request count may not represent downstream cost |
| Races/business logic | Concurrent or repeated operations can violate state invariants unless checks and effects share the required atomic boundary |
| GraphQL/gRPC/WebSocket | Object/message authority, stream lifecycle, batching, schema coercion and error semantics affect isolation |
| OAuth/OIDC | Client, redirect, state, nonce, PKCE, issuer and audience bindings have flow-specific roles and lifecycles |
| JWT/session | Signature validation, algorithm/key binding, claims, rotation, revocation, expiry and session lifecycle are distinct properties |

Redirects, duplicate parameters, encoding layers and filters can create interpretation differences across trust boundaries. A filter bypass alone does not establish an application-level security consequence.

## Parser, proxy and browser semantics

Duplicate query/form parameters, JSON keys, cookies and headers can become a scalar, list, concatenation, rejection or different selected value at different layers. Selection depends on the actual edge validator, framework binder and downstream consumer; a framework name does not establish a universal first/last-wins rule. A schema applied after duplicate keys were collapsed cannot detect their original multiplicity. Decoding order, Unicode normalization, type coercion and query/body precedence can change the value that is authorized or consumed. A second decoding pass after validation can reopen a boundary.

Distinguish the connection peer from caller-supplied forwarding headers and bind host/authority to actual routing. Strip untrusted copies before accepting identity or scheme assertions from a configured trusted proxy. SNI, HTTP authority and certificate identity serve different roles; connection coalescing and proxy termination mean universal string equality is not a sufficient routing policy. Request desynchronization depends on per-hop framing, downgrade behavior and connection reuse. Timing differences or rejected malformed messages alone do not establish a disputed request boundary or follow-on effect. Cache poisoning additionally needs the actual key, stored response and reuse context; reflection of an unkeyed value alone is insufficient.

CORS governs script readability and preflight permission; an unreadable response does not imply that no request was sent. CSRF depends on ambient credentials, an attainable request shape and a protected effect; a failed preflight for one shape does not protect every relevant shape. Cookie scope and SameSite have specific limits. For XSS, exploitability depends on decoding, sanitization and the final HTML/attribute/JS/URL or DOM sink. Server-rendered data can feed a DOM vulnerability. Inert reflection, scanner callbacks and execution confined to an analyst-modified page do not establish an executable victim path in the application's DOM or script context. Context-specific encoding, safe DOM APIs, configured sanitization and enforced CSP/Trusted Types have distinct roles; permissive policies or report-only headers do not make a sink safe.

## Object, function and field authorization

Bind the authenticated principal to resource, operation and current policy rather than trusting a submitted owner, tenant or role. Constrain the selected object to that authority, or perform an equivalent check before returning data or committing effects. Parameterized database access does not establish ownership. Opaque IDs, hidden routes and disabled introspection are discovery barriers rather than authorization. Validate relevant linked-object relationships and response fields: an authorized parent does not automatically authorize every child, attachment, export or sensitive property.

Mass assignment concerns authority-bearing fields as well as identifiers: roles, owner/tenant links, approval state and server-computed totals need server-side policy. Function-level authorization and response-field filtering are separate from write binding. Method overrides, content types and legacy versions matter when they reach a different handler or binder; do not assume every representation shares checks. Authorization-derived caches must preserve identity/tenant/policy scope. Signed object URLs delegate the capability their signature covers; expiry, method/object scope and revocation differ, and signing does not generally make a URL single-use.

Apply the relevant policy separately to current content, drafts and retained revisions. A correct current-object check does not establish that history, previews or exports enforce the same boundary; a local reconstruction also does not establish how a deployed version handles those paths.

## Interpreter, file and fetch boundaries

SQL parameterization binds data values; dynamic identifiers, sort expressions and query structure need separate constrained construction. Typed query APIs remain unsafe if caller data controls operators or raw fragments. Structured process arguments avoid shell parsing but may still permit target-program option injection. SSTI requires data to become template source or an evaluated expression; arithmetic-looking output alone does not identify the engine or establish host-runtime access. Impact depends on exposed objects, resolvers and implementation. Prototype pollution needs an unsafe property write and a reachable consumer of the affected inherited property; changing a prototype alone is not code execution.

Object-deserialization execution claims need attacker influence over type construction or behavior, plus reachable constructors/hooks/gadgets under the actual runtime, classpath and filters. A format signature, dependency name or ordinary JSON parse does not establish that chain. Data-only parsers can separately have memory-safety, resource or logic defects. Distinguish integrity checking before construction from checking after hooks already ran; a signature also does not constrain what an authorized producer may encode. Prefer data-only formats and explicit type schemas over gadget denylists.

SSRF depends on what the fetcher can actually send: method, headers, body, protocol, redirects and response access. A callback may originate from a browser, scanner or server; DNS resolution alone does not establish an HTTP request or metadata credential access. Apply URL policy to parsed authority and resolved destination, account for IPv4/IPv6 and alternate representations, and revalidate redirects. Prevent validation/connect DNS races through the resolver/egress design. Signed callbacks or URL syntax checks alone do not constrain reachability. For XXE, distinguish DTD parsing, external general/parameter entities, schemas, XInclude and XSLT; controls and defaults differ. An XML error or enabled DTD support alone is not demonstrated disclosure or execution.

For uploads/archives, bind inspected bytes/version to bytes later processed or served. Extension, MIME and magic prefix are individually weak evidence. Converters and previewers are additional consumers whose interpretation may differ from the initial upload parser. Constrain resolved extraction paths, symlinks and overwrites within the intended directory; textual prefix checks are insufficient. Separate storage execution permission from browser rendering and download authorization. Re-encoding or attachment headers address particular consumers, not every parser or identity boundary; storage acceptance does not prove installation, execution or public readability.

## Token, key and flow trust

A decoded JWT is unverified data. Establish expected token purpose and validator: signature, allowed algorithm/key type, issuer, audience and required lifetime/subject/client bindings are separate checks. Select keys from trusted issuer configuration and scope `kid` to that set; token-supplied `jwk`, `jku`, `x5u` or issuer URLs are not new trust anchors. Key discovery must not become unconstrained fetching or filesystem/database lookup. Handle unknown critical headers, ambiguous claims and unsupported token types explicitly. JWS does not hide payloads; JWE confidentiality does not itself establish every issuer or sender-authentication property. ID tokens, access tokens and proof tokens have different consumers/rules. Algorithm confusion requires a verifier accepting the wrong algorithm/key relationship, such as an asymmetric public key mistakenly used as a symmetric MAC secret; a changed header alone is not a bypass.

For OAuth/OIDC, bind authorization response and code redemption to the initiating browser session, expected issuer, client and registered redirect under the flow's rules. Bind the stored PKCE challenge and method to verifier validation, including the applicable profile's S256 requirements, and reject downgrade paths; PKCE does not replace resource authorization or every account-linking check. Enforce code single use and applicable client/redirect bindings at redemption. Verify the flow's required CSRF/nonce protections, actual session binding and replay behavior; parameter presence alone is insufficient. Native loopback redirects and other profile exceptions need specific matching rules, not blanket URL-prefix matching. Account linking must authenticate the account being linked and current user; use stable issuer/subject identity rather than unverified or reassigned email alone.

Rotation, revocation, refresh-family reuse and sender constraints are lifecycle properties, not consequences of an initial valid signature. For DPoP/mTLS, verify token key binding and applicable proof/request or TLS peer identity, including deployed replay/freshness rules. A copied public certificate, token `typ` or proof for another request is insufficient. Browser cookie/session defenses depend on the flow; fixed clock-skew limits, universal cookie settings and historical OAuth draft requirements should not be transplanted without current profile/deployment context.

## Graph and streaming APIs

GraphQL authorization follows resolved objects, fields and mutations, including global-node lookups and relevant nested relationships. Encoded IDs/cursors are not authority. Loader/cache state must not leak results between identities. Batches/aliases can multiply operations behind one HTTP request; accounting should reflect relevant operation/resolver work, cardinality and output size rather than only request count or depth. Introspection/errors establish exposure at the observed level, not unauthorized data access. Syntax or forbidden fragment cycles rejected before execution do not by themselves demonstrate resource exhaustion.

For gRPC, bind method/object authorization to authenticated metadata and decoded messages; HTTP success alone is not the final RPC outcome. Protobuf presence/defaults and gateway JSON conversion affect validation. For WebSocket/subscriptions, distinguish handshake, connection initialization and message authority. Browser attacks need actual credential/origin behavior; a custom client can forge Origin. Long-lived streams need the protocol's policy for expiry, role changes and resubscription rather than assumed indefinite authority. Handshake success does not establish authority for every later operation or message.

## Transactions, concurrency and replay

Authorization, current resource state, remaining balance or quota, version checks, idempotency reservation and resulting effects can share an atomicity requirement. A pre-check followed by an unlocked mutation can race. Transactions, locks and conditional writes provide different guarantees depending on the storage backend, isolation, rollback and retry semantics.

Business-state validity includes units, numeric domain, rounding and cumulative effects: individually permitted refunds can still exceed the original payment in aggregate. Derive prices, entitlements, completion and time windows from authoritative server/payment state rather than a client success screen or supplied timestamp. Serial retries, reordered callbacks and concurrent requests are different mechanisms. A uniqueness constraint, atomic conditional update or transaction enforces a specific invariant; a process-local lock or isolation-level label alone does not establish distributed exactly-once effects.

Idempotency depends on key scope and the complete request fingerprint. Current caller authentication and authorization remain relevant before a replay is served; a cached success is not a new authority path. Exact replay, conflicting replay, concurrent in-flight replay, failed operations and post-commit retries are distinct cases. Legitimate replay may remain valid after the successful operation changes the state that originally permitted it. Mutable cached results can allow later callers to alter the apparent historical response.

An in-memory lock does not establish distributed exactly-once behavior or crash durability. Response values and committed authoritative state are distinct protocol outcomes.

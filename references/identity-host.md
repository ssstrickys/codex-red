# Identity and host privilege boundaries

## AD and hybrid identity

AD and hybrid identity authority depends on principals, group memberships, object ACLs, trust edges, delegation, certificate enrollment, federation and effective privilege. A configuration graph is a time-specific representation that can contain stale edges; a possible path does not establish a completed authorized transition.

Resolve account realm and SID/object ID before equating names across local, domain and cloud identities. Authentication success proves credential acceptance for that protocol, not local administration or access to another service. SMB share and filesystem checks, WinRM endpoint policy, remote logon rights and token filtering can produce different access for the same account. Group changes may require a new logon/token or ticket; a directory membership snapshot is not the effective token of an existing process.

Interpret an AD ACE against its actual object type, attribute/extended-right GUID, inheritance, deny entries and protected-object behavior. `GenericWrite` is not permission to perform every account operation; password reset, membership changes, SPN writes and replication rights have distinct access checks. `WriteDacl` grants the ability to change an applicable DACL, not immediate access to every downstream resource. GPO control needs both the relevant directory/file permissions and application to a target within its scope and filters. A trust permits specified authentication paths; trust direction, selective authentication and SID filtering still constrain authorization.

Kerberos and certificate vulnerability classifications depend on identity bindings, service or issuer configuration, policy and patched behavior. A scanner label or administrative-looking tool banner is not proof of effective permissions.

Bind Kerberos observations to the KDC/realm, client principal, target SPN and service key. A TGT or successful ticket request is not evidence of application access. Constrained delegation and resource-based delegation use different policy locations; service identity, KDC rules, allowed target services and restrictions on delegating the requested user matter. For certificate authentication, enrollment permission, template purpose, subject/SAN control, approval/signature requirements, CA trust and account-mapping policy must form a usable chain. Strong-binding enforcement and patched behavior can invalidate older ESC recipes. Hybrid federation adds issuer, audience, tenant and cloud-role checks; on-premises control does not by itself establish an Entra role or cloud session.

## Linux and Windows privilege models

Host privilege boundaries depend on OS/build, effective identity and groups, process tokens or capabilities, filesystem and service permissions, scheduled tasks, IPC, drivers, sandbox boundaries and installed mitigations. Caller-controlled data or configuration becomes a privilege concern when a consumer acts on it with different authority.

Linux and Windows expose different privilege models. Linux namespaces, capabilities, mount options, SUID/service execution and dynamic loading differ from Windows tokens, integrity levels, service/object permissions, impersonation, RPC/COM interfaces and driver IOCTL contracts.

On Linux, distinguish real/effective/saved IDs, filesystem credentials, supplementary groups and the user-namespace mapping. UID 0 inside a user namespace is not host root. Distinguish process permitted/effective/inheritable/ambient/bounding sets from file permitted/inheritable masks and the file effective flag. Exec transitions depend on both, namespace/root-ID rules and privilege constraints; privileged exec clears ambient capabilities. SUID bits or capability xattrs alone do not establish an elevation: `nosuid`, `no_new_privs`, execution context and program behavior affect the transition. Resolve directory traversal/ACLs, the actual mount and writable parent paths, not just a file's mode bits. For sudo, match RunAs identity, command/argument rules, environment handling and the installed policy; `NOPASSWD` does not authorize arbitrary commands. Secure execution can suppress loader environment variables, so an `LD_PRELOAD` value alone is not a load event.

Privileged command resolution depends on the command name, `PATH`, working directory, inherited environment and effective execution context. A writable search location matters only if that consumer reaches it. Keep privileged file access separate from an interactive elevated shell or unrestricted execution.

On Windows, identify the effective thread impersonation token or process primary token, enabled/deny-only groups, restricted SIDs, privilege state, integrity level and logon/session context. A present privilege is not necessarily enabled or exercised. `SeImpersonatePrivilege` needs a usable token source and a permitted impersonation path; it does not create a SYSTEM token. UAC elevation of a filtered administrator token differs from granting administrator membership to an ordinary user. Service configuration permissions, service-object DACLs and executable-directory permissions are separate. An unquoted path matters only when actual path parsing reaches an attacker-writable candidate and a higher-authority service executes it. DLL substitution requires a relevant search/load path, compatible binary and applicable loader/signing policy. A writable service file or task definition also needs a privileged consumer and a reachable load/restart/trigger; a configured task is not an execution event.

Configuration weakness, local code execution, elevated privilege and kernel impact are distinct claims. Privileged file access alone does not establish an interactive elevated shell or unrestricted execution.

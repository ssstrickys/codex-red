# Cloud, containers, and Kubernetes

Cloud authority depends on the account/project/subscription, region, caller identity, resource and applicable policies. Identity policies, resource policies, trust relationships, inherited restrictions, explicit denies and workload credentials have different roles. A reachable endpoint, listed permission or policy-simulator result does not by itself establish usable authority.

For AWS, distinguish the identity/resource-policy grants from limits imposed by session policies, permissions boundaries and organization policies. Boundaries and SCPs do not grant permissions; applicable explicit denies override allows. Resource-policy treatment of a user, role and assumed-role session differs, so do not apply a universal intersection rule. Cross-account role assumption needs caller-side authorization and the target trust policy, with its principal, MFA, external-ID, tag and other conditions satisfied. Evaluate the resulting session's permissions separately from permission to obtain it. `iam:PassRole` is not `sts:AssumeRole`: a service path also needs the relevant create/update operation, an eligible role trusted by that service, permitted resource/configuration choices and a way for the submitted workload to exercise that role.

For Azure, separate Entra directory roles, Azure management-plane RBAC and each service's data-plane authorization. Resolve assignment scope/inheritance, deny assignments, conditions and actual PIM activation; eligibility is not an active grant. Credential-write access to an application can expose its already-granted service-principal permissions; it does not itself grant new tenant roles or admin consent. Bind application/service-principal identities and delegated versus application tokens to the intended tenant, audience and granted permissions. A managed identity inherits the permissions assigned to it, not the privileges of a human who can inspect the resource. For GCP, evaluate inherited and resource-local permissions, IAM Conditions, deny and organization policies; service-account `actAs`, token creation and key creation are distinct powers. Creating a workload does not imply access to an arbitrary service account or an Editor identity. Attached identity and credential/scopes restrictions determine the workload authority; historical default service-account grants may not apply.

Storage policy, cross-account trust, workload identity, metadata controls, deployment authority, encryption-key policy and network placement can independently constrain cloud data access.

Metadata reachability is only one prerequisite: required request methods/headers, token flow, network placement, workload identity bindings and credential audience still matter. Do not infer credential disclosure from a generic SSRF or a reachable metadata address. Likewise, storage listing, object reads, decryption-key use and snapshot access can have different authorization checks; one successful operation does not establish all data access.

Container image flaws, process privilege, host mounts, runtime configuration, capabilities, namespace isolation and host-kernel vulnerabilities are distinct properties. Runtime and kernel versions affect their meaning. A privileged-container configuration alone does not establish a completed host escape.

Interpret capabilities in their owning user namespace together with UID maps, seccomp/LSM restrictions, devices and mount propagation. `CAP_SYS_ADMIN` or `CAP_SYS_PTRACE` inside a container does not automatically authorize operations on host resources. Comparing two namespace links inside one container cannot identify a host namespace without a host reference. A mounted daemon socket matters only if the process can use its API and that daemon controls the disputed host; rootless or restricted daemons change the outcome. Cgroup v1 release-agent techniques require the relevant v1 facility, writable configuration and sufficient authority in the governing namespaces; do not extrapolate them to cgroup v2 or infer them from one capability bit.

Kubernetes authority combines service-account identity, RBAC verb/resource relationships, admission policy, network policy, Secret access paths, node/cloud identity, kubelet/API exposure and controller behavior. Namespace and identity context constrain the effective result.

Bind a service-account token to issuer, subject, audience, expiry and any bound object; a projected token is not necessarily a permanent credential. RBAC authorization and admission are separate: pod creation may provide indirect access through a chosen service account, mounted Secret or node feature even without direct Secret reads, but allowed pod fields and admission controls determine the path. `bind`, `escalate` and `impersonate` have specific target/scope checks, not generic administrator meaning. NetworkPolicy enforcement depends on the CNI, selected pods and policy direction. Allow rules combine within a direction, but traffic must satisfy both source-egress and destination-ingress isolation where each applies; node/host-network handling is implementation-dependent. A policy object's presence or a NodePort alone does not prove traffic is blocked or bypassed.

Provider-specific policy semantics, defaults and available features depend on the deployed service and current configuration.

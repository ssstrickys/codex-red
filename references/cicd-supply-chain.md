# CI/CD and software supply-chain security

CI/CD trust boundaries connect contributor-controlled input, build execution, dependencies, signing, artifact publication and deployment. Secrets access, repository write permission, signing authority and deployment credentials may belong to different execution contexts. Trigger event, checked-out revision, token context and runner configuration determine whether an external contributor can reach a privileged consumer; local execution alone does not establish that relationship.

For GitHub Actions, distinguish a fork `pull_request` execution from `pull_request_target` running in the base repository context. The dangerous transition is privileged execution of contributor-controlled code/data, such as checking out the untrusted head and executing its build scripts; the event name alone is not a finding. Repository/organization settings, fork approvals, reusable-workflow permissions and environment protection determine actual token/secrets access. A later `workflow_run` job can cross a privilege boundary when it trusts outputs of a less-trusted run; bind the producing repository, run, head SHA and artifact identity to the consumer's authorization decision. Apply the corresponding fork/protected-ref and variable rules for the actual GitLab, Jenkins or Azure DevOps configuration rather than importing GitHub defaults.

Distinguish expression evaluation, generated script source and runtime data expansion. Untrusted values interpolated into a shell/program source can become syntax before execution. Passing a value as an environment variable or argument with correct quoting usually keeps it data, unless a later `eval`, shell invocation or template stage reparses it. Trace that later consumer before claiming injection. Secret masking does not constrain what a running job can read, and shell escaping does not change the job's authority.

OIDC token issuance and cloud authorization are separate steps. A job's `id-token: write` permits requesting an identity token, not assuming every cloud role. Match verified issuer/audience and actual subject/ref/environment or reusable-workflow claims to the cloud trust policy; branch protections and approvals must apply to the identity asserted in that token. Claim formats and provider-supported conditions vary. For persistent runners, contributor code may affect workspaces, credentials or later jobs beyond the current token lifetime; establish runner assignment and cleanup boundaries before inferring cross-job impact.

An artifact name, cache key or branch label is not provenance. Resolve who can populate the particular store/scope, which producer commit/run the consumer selects, and whether its content is executed, unpacked or merely parsed. Cache visibility, write scope, version keys and concurrent jobs are platform-dependent; a matching key alone does not establish a lower-trust writer can poison a privileged restore. Mutable image/action tags can change future inputs; a digest/commit pin binds content but still needs an approved origin and update path. Attestations must bind the artifact digest to an accepted builder identity, source revision and materials under the verifier's trust policy. A valid signature from an untrusted or compromised build does not establish an approved build.

Package selection depends on resolver configuration, namespace ownership, lockfile constraints, registry precedence and integrity enforcement. Lifecycle hooks can execute code after selection. A public package with the same name alone does not establish dependency confusion or compromise.

Use the installed resolver's semantics: npm scope-to-registry mappings differ from unscoped defaults; pip `--extra-index-url` adds candidates rather than establishing a trusted fallback order. Version constraints, direct URLs, hashes and local caches can change the selected candidate. NuGet package-source mapping and client/project restore behavior matter; feed order is not a universal security boundary. Maven/Gradle dependency, plugin and buildscript resolution may use different repositories and cached metadata. Follow transitive dependencies and lifecycle/build hooks separately: selecting a package, executing its code and deploying a derived artifact are different outcomes. A lockfile or matching hash proves a pinned selection/byte identity only to the extent the active installation path enforces it; neither authenticates a trustworthy publisher by itself.

A secret-looking value may be synthetic or inactive. Exposure, current credential validity, permission scope and resulting access are separate properties. Credential validation and rotation can change external systems; a visible string alone does not establish those effects.
